## Team access and encryption

Site authentication supplies a stable signed-in identity. Each property has an owner, membership list, employee/account associations, explicit capabilities, and authority scopes. Invitations bind to the signed-in email, then require administrator approval and key provisioning. Invitations use URL fragments so invitation tokens are not sent in page-request URLs. Ordinary users cannot grant themselves access. The owner cannot be disabled through the application.

Scope checks support property, department, primary position, specific employees, reporting lineage, and direct reporting relationships. Title alone never grants software permission. The backend checks every resource read, write, delete, and key recipient. Data and wrapped keys outside authorized scope are withheld. Operations with property-wide configuration or recovery authority require property-wide administrative grants.

The browser encrypts each record with a random AES-256-GCM key. Record identity, property, module and employee scope are authenticated as associated data. Keys are wrapped to authorized account RSA-OAEP keys. Coaching, discipline, scheduling preferences, availability, general employee profiles, and other legacy private employee attributes use separate resources and permissions. Schedule viewing does not expose availability or private employee details. Field keys are rotated for changed records and membership provisioning; historical ciphertext stays unchanged while authorized historical key envelopes can be provisioned separately.

The server stores ciphertext, wrapped keys, and the minimal identifiers, scope directory, account identity, and shift-boundary metadata needed to authorize requests and reconstruct snapshots. It does not routinely decrypt hotel record contents. Authorization and delivered application code remain trusted server/platform responsibilities; this is not a claim of protection against a compromised client or malicious replacement application code.

The existing owner-only encrypted workspace is retained as a migration fallback. A client decrypts it and migrates records into the new model. Browser storage contains an account key and an encrypted working copy. Account recovery files separately encrypt the account private key with a passphrase. A different full administrator can approve a replacement account key, revoke prior sessions, and provision current and historical record keys from their authorized client. If all authorized account keys and recovery files are lost, the server cannot reconstruct the plaintext.

## Sessions, audit, and history

Application sessions use random tokens stored only as hashes, HttpOnly/Secure/SameSite cookies, a 12-hour expiry, session review, and revocation. Disabling membership prevents future property access even after starting another session. These controls govern EasyMan sessions and membership; they do not revoke the identity provider's account or OAuth sessions.

Writes require same-origin requests and bounded streamed bodies. APIs rate-limit requests. Production responses include a nonce-based script CSP, nosniff, referrer and permissions headers. Encrypted revisions, writes, leases and audit events commit together. A unique revision lease prevents concurrent stale batches from silently overwriting another session. Security history has no property-user delete endpoint. It is application-immutable, not protected from an infrastructure administrator who controls the database.

Audit events cover session creation, membership changes, account recovery, key provisioning, confidential-record changes, configuration changes/exports, schedule publication requests and record publication writes, and automatic snapshots. Events contain identifiers and action metadata, not decrypted descriptions.

## Automatic shift snapshots

The snapshot service reconstructs pass-on state at a configured boundary from current encrypted records and their historical encrypted versions. A record completed after handover remains open in that handover capture. Captures contain pass-on records only, with boundary, closing/incoming context and immutable encrypted contents. Duplicate capture requests are idempotent. The browser can request due captures and display them without server decryption.

`/mcp` exposes owner-authenticated `capture_shift_snapshots` and read-only `snapshot_status`. The private EasyMan connector is connected and an authenticated capture call was verified. The linked hourly background task captures due boundaries; every completed non-browser check records a metadata-only receipt, even when no new snapshot is due. Shift pass-on → Snapshots displays that receipt without creating one. The service records exact boundary timestamps and state, but scheduled task start times can be delayed by the scheduler. Catch-up resumes from the latest captured boundary (or property creation), processing up to 31 calendar days per run so a later run can continue a longer outage. There is no push, email or SMS notification system in the app.
