# EasyMan 0.2 development release

The remaining V1 application work is implemented as a development build. The final **1.0 release is held** pending GitHub App configuration and acceptance checks. The owner supplied the private feedback repository on October 9, 2026; its destination is configured. This document distinguishes implementation from infrastructure setup and validation.

## Implemented workflows

- Responsive dashboard and permission-aware navigation, sample-property setup, configurable property identity and time zone.
- Shift pass-on creation, ownership, notes, related follow-ups, escalation, completion/archive, overdue indicators, and privacy-conscious 16:9 PNG briefings using only pass-on items.
- Weekly schedule generation with qualifications, hard availability restrictions, recurring unavailable weekdays, date ranges, position/shift-specific restrictions, configured rest and weekly-hour expectations, seniority tie-breaking, preferences, workload balancing, and a bounded gap-repair heuristic. Drafts can be edited, partially regenerated by selected days, and published. Unselected days constrain partial generation. Per-employee publication state and encrypted publication history retain the original shift times.
- XLSX schedule and room board exports, including overnight end dates, numeric totals, and leading-zero room numbers.
- Housekeeping workload balancing, locks, cleaning progress, scoped reassignment, temporary score/flag overrides, and DND tasks retained outside active cleaning assignments.
- Room check logging with linked rechecks and separate inspection history. Results do not generate disciplinary decisions.
- Coaching and discipline records with scoped access, editable fields, append-only follow-ups, preserved previous content, incident timestamps, and immutable encrypted server revisions.
- Employee creation/editing, additional department affiliations and position qualifications, availability restrictions, and position-based or individual reporting relationships. Circular reporting paths are rejected.
- Manual department, position, shift, room-type, staffing-rule and room configuration. Referenced items cannot be removed. Positions and requirements can be disabled. Staffing rules support weekday and date-range overrides.
- Validated JSON imports with schema/example/conversion prompt, preview, reference checks, calendar validation, resource limits, and explicit commit. Unsupported employee fields are rejected rather than silently shared.
- Encrypted and explicitly acknowledged unencrypted configuration exports, safe backup restoration, missing-default merging, default restoration, encrypted working-copy export and previewed merge restoration.
- Feedback compose/review, encrypted draft persistence, idempotent server-side GitHub App submission, repository-privacy verification, and failure/uncertain-submission handling. The three categories remain Pain Point, Bug, and Feature Request.

## Team access and encryption

Site authentication supplies a stable signed-in identity. Each property has an owner, membership list, employee/account associations, explicit capabilities, and authority scopes. Invitations bind to the signed-in email, then require administrator approval and key provisioning. Invitations use URL fragments so invitation tokens are not sent in page-request URLs. Ordinary users cannot grant themselves access. The owner cannot be disabled through the application.

Scope checks support property, department, primary position, specific employees, reporting lineage, and direct reporting relationships. Title alone never grants software permission. The backend checks every resource read, write, delete, and key recipient. Data and wrapped keys outside authorized scope are withheld. Operations with property-wide configuration or recovery authority require property-wide administrative grants.

The browser encrypts each record with a random AES-256-GCM key. Record identity, property, module and employee scope are authenticated as associated data. Keys are wrapped to authorized account RSA-OAEP keys. Coaching, discipline, scheduling preferences, availability, general employee profiles, and other legacy private employee attributes use separate resources and permissions. Schedule viewing does not expose availability or private employee details. Field keys are rotated for changed records and membership provisioning; historical ciphertext stays unchanged while authorized historical key envelopes can be provisioned separately.

The server stores ciphertext, wrapped keys, and the minimal identifiers, scope directory, account identity, and shift-boundary metadata needed to authorize requests and reconstruct snapshots. It does not routinely decrypt hotel record contents. Authorization and delivered application code remain trusted server/platform responsibilities; this is not a claim of protection against a compromised client or malicious replacement application code.

The existing owner-only encrypted workspace is retained as a migration fallback. A client decrypts it and migrates records into the new model. Browser storage contains an account key and an encrypted working copy. Account recovery files separately encrypt the account private key with a passphrase. A different full administrator can approve a replacement account key, revoke prior sessions, and provision current and historical record keys from their authorized client. If all authorized account keys and recovery files are lost, the server cannot reconstruct the plaintext.

## Sessions, audit, and history

Application sessions use random tokens stored only as hashes, HttpOnly/Secure/SameSite cookies, a 12-hour expiry, session review, and revocation. Disabling membership prevents future property access even after starting another session. These controls govern EasyMan sessions and membership; they do not revoke the identity provider's account or OAuth sessions.

Writes require same-origin requests and bounded streamed bodies. APIs rate-limit requests. Production responses include a nonce-based script CSP, nosniff, referrer and permissions headers. Encrypted revisions, writes, leases and audit events commit together. A unique revision lease prevents concurrent stale batches from silently overwriting another session. Security history has no property-user delete endpoint. It is application-immutable, not protected from an infrastructure administrator who controls the database.

Audit events cover session creation, membership changes, account recovery, key provisioning, confidential-record changes, configuration changes/exports, schedule publication requests and record publication writes, and automatic snapshots. Events contain identifiers and action metadata, not decrypted descriptions.

## Automatic shift snapshots

The snapshot service reconstructs pass-on state at a configured boundary from current encrypted records and their historical encrypted versions. A record completed after handover remains open in that handover capture. Captures contain pass-on records only, with boundary, closing/incoming context and immutable encrypted contents. Duplicate capture requests are idempotent. The browser can request due captures and display them without server decryption.

`/mcp` exposes the owner-authenticated `capture_shift_snapshots` tool for unattended use. **The private EasyMan connector must be connected and its background task configured before closed-browser execution is considered operational.** The service records exact boundary timestamps and state, but scheduled task start times can be delayed by the scheduler. Catch-up resumes from the latest captured boundary (or property creation), processing up to 31 calendar days per run so a later run can continue a longer outage. There is no push, email or SMS notification system in the app.

## Validation

TypeScript and production build checks run before publication. Automated tests cover constraints and partial regeneration; hard overnight unavailability; calendar/import failures; locks, DND and configured qualifications; reporting cycles; capability/scope checks; recipient-specific keys; associated-data tampering; recovery-file passphrases; workbook privacy and interoperability structure; and actual API handlers using an isolated SQLite database and a simulated trusted platform-auth boundary. API checks cover denied scope, key recipients, CSRF, stale revisions, revoked sessions and disabled membership. Snapshot tests verify exact historical boundary state and idempotency. A real local preview separately rejects spoofed authentication headers.

Browser QA verifies legacy migration, existing housekeeping progress, encrypted saves/reloads, team/session review, scoped navigation controls, and partial regeneration. Feedback handler tests verify GitHub App JWT signatures, repository-limited tokens, all three category labels, public/archived/disabled-issues rejection, bounded input, account ownership, rate limits, concurrent deduplication, safe retries and ambiguous-submission blocking. GitHub CI is configured to run type checks, tests and the production build. External feedback and unattended connector execution must be validated after their owner setup.
